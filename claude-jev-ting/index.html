Can an AI agent do real work for a fraction of the usual cost and time, by letting an expensive "frontier" model do only the thinking that needs it, and handing the many small decisions to a cheap, fast model we host ourselves?

The long-term goal is business agents (browser workflows, operations, back-office tasks) that spend far fewer tokens and finish faster. We're proving the idea on code first. Code comes with an honest referee built in: its tests. That means every result can be checked without trusting any AI's opinion.

The idea in one picture

Most of an agent's steps aren't open-ended thinking. They're multiple-choice questions: which file next? is this the right function? which suspect first? So the system writes out the options, a small model picks, and something reliable checks the result.

Frontier modelPlans, and writes the actual code change. Called rarely.
→
Jev (cheap model)OpenJev, 27B, on a rented GPU. Picks from menus of options. Called often, in ~0.4 s.
→
ChecksPlain code: search tools, the project's own tests. Decides what actually worked.

Two rules hold it together. Models propose, the system disposes: nothing a model says is executed without being checked. Truth comes from code and tests, never from a model: the frontier model is one of the things being measured, not the judge.

Step 2: fixing bugs (done, first version)

Finding code isn't doing work, so next the agent had to fix things. To grade that honestly, we broke real code on purpose, one tiny change at a time, and kept only breaks that the project's own tests catch:

return this.protocol === 'https'   // original
return this.protocol !== 'https'   // our planted bug → the tests now fail

160 bugs like this, in two popular JavaScript projects (koa and commander). The agent sees only what a developer would ("these tests fail"), has to find the broken function, write a fix, and run the tests, all inside a locked-down container with no internet.

The interesting part was why it failed. Handed the broken function, the frontier model fixes it 98% of the time, so fixing is easy and finding is hard. The search found the right function only about half the time. It behaves like someone skimming files who stops at the first thing that looks relevant. But many functions are about the same topic, and only one has the bug.

Step 3: a better way to find bugs (done, and it works)

So we changed the shape of the agent from "search until something looks right" to make a shortlist → put it in order → check each one:

  1. Shortlist, with no AIRun the tests and record which functions the failing tests actually use. The bug has to be one of them, usually one of 25–70. Functions used mostly by failing tests go first.
  2. Order the shortlist, with a modelA model reads the top 8 suspects and puts the likeliest first.
  3. Check, with the testsFix suspect #1 and run the tests. If they still fail, undo and try #2, up to 5. The fixer may also say "the bug isn't here", and it never said that about the real bug.

The cheap model orders suspects as well as the frontier model (111 vs 114 is within noise), about 8× faster and with 28% fewer frontier tokens per fix. And it knows when it's unsure: when Jev is at least 90% confident it's right 99% of the time. So the plan is to ask the frontier only on the few calls where Jev hesitates. Replaying this run, that means asking it about 1 time in 9 and matching its results.

What we've learned so far

  1. The menu matters more than the chooser. Most of our gains came from giving the models better options, not better models. If the right answer isn't on the menu, no model can pick it.
  2. The cheap model knows when it's unsure. Its confidence is honest: above 90% it's almost never wrong, which is what makes "ask the frontier only when needed" workable.
  3. The cheap model is at least as good at choosing. Decision by decision on the bug-fixing runs, Jev was right slightly more often than the frontier model (e.g. 67% vs 59% when judging code, 86% vs 79% when picking lines).
  4. Measure honestly, or you'll fool yourself. The same setup run twice disagrees on 6–17% of answers. One "significant" result turned out to be noise, so we compare with the plans held fixed and repeat runs.
  5. Tests are a good referee, not a perfect one. A few "fixes" passed by deleting logic the tests happened not to check. Any training data has to be cleaned for that.
  6. The hard part is knowing where to look. Which options even make the menu is where domain knowledge lives. For code, test coverage tells us; for other domains the system will need to learn how to build its own menus.
