Can a coding agent spend far fewer frontier-model tokens on the same work, by handing its many small decisions to a cheap, self-hosted classifier, without getting worse at the job?

So far: yes, on code search. On 428 questions across 15 real open-source repos, the split system matches a frontier-only agent on quality while using about 12× fewer frontier tokens. The next step is making the agent change code, not just find it.

How it works

A frontier model is good at open-ended reasoning and expensive per token. Most of an agent's steps aren't open-ended: which of these files do I read next? does this excerpt answer the question? which lines are the answer? Those are multiple-choice questions, so the runtime builds the menu and a small model picks from it.

PlannerFrontier model (OpenAI). Writes the search plan once, and re-plans only when stuck.
→
Router + judgeOpenJev, a 27B open classifier on a rented H100. Picks from menus the runtime builds.
→
ToolsDeterministic and read-only: search, read, list, function outlines.

Two rules hold everything together. Models propose, the runtime disposes: every model output is schema-validated and policy-checked before anything runs. And truth comes from code and tests, never from a model: answer keys are chosen by our own code before a model writes the question's wording, and the frontier model is one of the systems being measured, not the referee.

Results so far

The eval set covers 15 pinned repos in 6 languages (koa, express, axios, commander, pino, got, click, requests, flask, chi, cobra, gin, serde-json, http, gson, jsoup). Questions are phrased two ways: as a user would ask them, and as a precise planner-level lookup. Some questions have no answer in the repo, and the right move is to say so.

Frontier-only uses OpenAI's cheapest tier for routing and judging. Both use the same planner. The GPU for Jev cost about $0.23 for a 163-question run at 8 tasks in parallel. Idle time and startup cost more than the work itself.

What we learned

  1. The planner is the biggest lever. Code-shaped search terms (setTimeout, AbortController) beat the words in the request.
  2. What the menu offers matters as much as who chooses. Most gains came from the runtime: fair judge wording, file roles, read windows snapped to whole functions. The model weights were the same. At one point, 43 of 50 misses were "the right answer was never on the menu".
  3. The small model is good at saying no. Early on it answered "not in this repo" correctly 20/21 times vs 14/21, and made up 1 answer vs 7.
  4. Evaluation hygiene decides what you believe. An unfair judge prompt, an incomplete answer key, and out-of-credit errors graded as misses each produced a convincing wrong number at some point.
  5. Runs aren't deterministic. The same configuration flipped 13–17% of answers between two runs, because the frontier planner samples differently each time. One "significant" result (p = 0.043) turned out to be noise. Replaying the same plans across configurations cut the flips to 3.3%, and that's now how configurations are compared.

Where it's going

Done

Find it. Eval harness, the split agent, a self-hosted classifier, function-level options, and plan replay for fair comparisons.

Now

Fix it. An agent that changes code. Tasks are made by breaking real functions on purpose (mutation testing). The repo's own test suite decides whether a fix worked. Code runs only in a throw-away copy, inside a container with no network.

Next

Confidence cascade. The small model decides, and the frontier is consulted only when it's unsure. That gives a dial between cost and quality, and every consultation is logged as a labelled example.

Later

Distillation, carefully. Train the small model on strong teachers' decisions, possibly from several providers. Teachers are wrong too, so a label is kept only if it agrees with the tests or answer key and with the other teachers, and survives a red-team pass.
